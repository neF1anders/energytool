## 2. Ключевые решения и отступления от спеки

1. **tiktoken убран.** Ему нужна сеть для словаря, а в контейнере проверки её может не быть. Токены оцениваются как `len/3.5`.
2. **rapidfuzz убран.** Сверка цитат в reducer сделана на stdlib `difflib`, домен остался без зависимостей. Ядро теперь: `httpx`, `numpy`, `bm25s`.
3. **Thinking Qwen.** OpenRouter молча игнорирует `chat_template_kwargs`: ответ приходил пустым (`finish_reason=length`), и всё уходило в шаблон. Это нашёл прогон ZIP с профилем `platform`. Решение — **калибровка на старте**: пробный запрос на каждый вариант (`chat_template_kwargs`, `reasoning.enabled=false`, без параметров). Дополнительно пустой ответ повторяется с лимитом ×4. Действует на платформе тоже.
4. **Число берётся из цитаты клиента.** Extractor сам переводил «1,1 МВт» в 1100 и при этом возвращал `unit="МВт"`, из-за чего получалось 1 100 000 кВт. Reducer верит цитате, а уже пересчитанное значение повторно не умножает.
5. **Батч по умолчанию — наивный путь** (ретрив + Responder, без Extractor и вопроса анкеты): на судье он равен полному, а по времени вдвое быстрее (раздел 3). Полный конвейер — основной для веба; для платформы вариант собирается флагом `--env BATCH_PIPELINE=full`.
6. **`build_query` в батче не сужает область** (`restrict_scope=False`): у одиночного вопроса нет накопленного контекста. В чате — по спеке.
7. **Fallback ретрива** добавляет раздел вне области, только если тот прошёл бы в top-k. Иначе страховка превращается в шум.
8. **`after_retrieval`** — отдельная функция политики. `below_floor` известен только после поиска, поэтому переход «ответа нет → специалист» делается вторым шагом.
9. **Полные контакты одним сообщением** переводят в SUBMITTED из любого состояния. Дефект нашёл сквозной тест хлебозавода.
10. **`bootstrap_web.py` отдельно от `bootstrap.py`.** Последний достижим из `solution.py`, и импорт SQLAlchemy сломал бы ZIP. Сборщик ZIP также запрещает `from energytool.x import <подмодуль>`: после плоской раскладки такой импорт ломается только на платформе.
11. **Few-shot Responder синтетический.** Демо-эталоны — данные хакатона, в код и git они не копируются.
12. **Калибровка правил по `eval/dialog`.** Правило фото для УК/ТСЖ/СНТ вынесено в `PHOTO_HOUSING` с весом +1: при +2 у СНТ не было лидера.
13. **Расширения таблицы правил:** `GOAL_*`, `*_HYBRID`, `SOLAR_SLATE_UNKNOWN` (флаг), `OREM_ALREADY_PLATFORM`, `PHOTO_MANUAL` (полный список — spec §5.3).

## 7. Эксперименты после первой посылки (ветка `exp/score-tuning`, 2026-11-14)

Исходная точка: посылка из `main` (наивный путь, `hybrid_rerank`, top-4) — около 0.56 на публичной части. Балл считается относительно baseline с опорой на эталон, поэтому локально варианты сравнивались **с ответами `main`** (а не с учебным примером, у которого `main` выигрывает 0.9 и разницы между вариантами не видно): 0.5 — паритет с `main`.

Стенд: 18 демо-вопросов + 22 дополнительных вопроса с эталонами в стиле демо (границы продуктов, отказы, вне темы, диалоги; `eval/data/dev_extra.json`, только локально). Два промпта судьи (`--judge v1|v2`) и две модели судьи (Qwen 3.8 27B и модель другого семейства), чтобы не подгоняться под одного судью. Разброс на 40 вопросах — около ±0.03, различия меньше этого не считаются.

| Вариант | Судья 1 | Судья 2 | Вывод |
|---|---|---|---|
| новый промпт без вопроса в конце | 0.44 | 0.47 | хуже `main`: эталоны почти всегда заканчиваются вопросом |
| + вопрос в конце по умолчанию | 0.56 | 0.58 | |
| + отсечение слабых разделов, запрет лишних цифр, оговорки из ограничений | 0.60 | 0.63 | |
| + подсказки для вопроса из базы | 0.62 | 0.65 | |
| + структура «ответ → оговорка → вопрос» | 0.64 | 0.66 | |
| **+ ответ на условие клиента, соотнесение ситуации с продуктами (итог, A)** | **0.67** | **0.71** | в прямом сравнении с предыдущей строкой 0.60 |
| A + вопрос для поиска из диалога (C) | 0.68 | 0.72 | с A ничья (0.44, различаются только диалоги) |
| A с узким контекстом (top-4, ratio 0.6) | 0.56 | — | против A 0.37 — отброшен |
| A + карта продуктов в контексте | 0.66 | 0.63 | без прироста — отброшена |
| A + проход-редактор | 0.63 | 0.66 | против черновика 0.41 — отброшен |

Что дало результат:
1. **Стиль эталона.** Эталон — это прямой ответ, один-два факта по теме, оговорка «оценим отдельно» и один вопрос о клиенте. Лишние цифры («более 300 типов», «от 15 до 500 кВт») судьи считают непроверяемыми утверждениями.
2. **Разделы-ограничения базы в каждом ответе.** Эталоны берут оговорки именно оттуда (верификация показаний, вероятностный результат, порог 750 кВт), а поиск по вопросу клиента эти разделы не находит.
3. **Скор реранкера как фильтр.** Он хорошо откалиброван (вне темы — 0.01, по теме — 0.9+), поэтому хвост слабых разделов отрезается, а не подаётся в промпт.

Чего не делали и почему: смена чанкования и состава индекса — на демо разметке recall@6 уже 18/18, проигрыши шли от генерации, а не от поиска; полный конвейер в батче — по прежнему сравнению не лучше наивного.

Посылки (`dist/`, сборка `tools/build_submission.py`):

| ZIP | Конфигурация | Когда слать |
|---|---|---|
| `exp-a.zip` | умолчания ветки | первой |
| `exp-c-condense.zip` | `--env BATCH_CONDENSE=true` | второй, если в закрытой выборке много диалогов (локально равен A) |

Ограничения оценки: судья и baseline платформы неизвестны; дополнительные эталоны написаны нами по базе в стиле демо. Локальные 0.67–0.71 — это преимущество над `main`, а не прогноз балла на платформе.

## 9. Управление диалогом: отказ от продукта, пересмотр цели, вес площадки (ветка `exp/dialog-steering`, 2026-11-15)

Повод — ручной прогон веб-чата: клиент-хлебозавод хотел навести порядок в учёте и на 6-м ходу прямо сказал «не хотим солнечную энергию», а лидером до конца оставалась сетевая солнечная станция (P = 0.82), бот задал ещё три вопроса про кровлю, и бриф ушёл менеджеру с солнцем на первом месте. Причины в домене, общие для `main`, `exp/score-tuning` и `exp/context-tuning`:

1. отказаться от продукта было нельзя: в `Extraction` только `mentions`, они продукт поднимают, но не опускают;
2. цель (`goal = reduce_bill`) извлекалась на 1-м ходу и не пересматривалась, когда клиент переформулировал задачу («куда утекает электричество»);
3. ответ на наш же вопрос «крыша или земля?» давал солнцу +1.5 (`SOLAR_SITE`) и гибриду +1.0 — больше, чем «показания вручную» платформе учёта.

Изменения:

- **E1** — промпт извлекателя `extractor-v2`: поле пересматривается, если клиент сказал иначе; для `goal` берётся последняя формулировка (ошибки в расчётах, ручной сбор, «куда уходит электричество» у себя → `metering`; `loss_detection` — только сети и абоненты).
- **E2** — `Extraction.rejected` и `ConversationState.rejected` (продукт → ход отказа, кодек состояния v2, v1 читается). Правила `REJECTED_*` исключают продукт (как фильтры «не подходит»), в брифе — «клиент отказался от этого решения». Отказ снимается, только если клиент сам снова спросит о продукте; в одной реплике отказ сильнее упоминания. Вопрос или сомнение («а солнце нам не подойдёт?») отказом не считается.
- **E3** — площадка даёт солнцу полный вес только при интересе клиента: `SOLAR_SITE` +1.5 после упоминания солнца клиентом, иначе `SOLAR_SITE_WEAK` +0.5; гибриду +1.0 при упоминании, отключениях или цели «надёжность», иначе +0.3.

Стенд: `python -m eval.dialog.replay` — заданные реплики клиента (без LLM-клиента, варианты сравниваются на одинаковом входе), 2 прогона на сценарий: `bakery_leaks` (реплики ручного прогона без контактов), `warehouse_no_solar` (отказ на 2-м ходу), контроль `office_asks_solar` (вопрос про солнце — не отказ).

| вариант | bakery_leaks: лидер в конце | вопросов про солнце после отказа | P(солнце) в конце | склад: вопросов после отказа | контроль: лидер солнце |
|---|---|---|---|---|---|
| база (`exp/score-tuning`) | нет лидера, 0/2 | 3 / 3 | 0.58 / 0.62 | 1 / 1 | 2/2 |
| E1 | 1/2 | 1 / 5 | 0.24 / 0.65 | 2 / 1 (во 2-м прогоне лидер — солнце) | 2/2 |
| E1+E2 | 2/2 (учёт с 5–6-го хода) | 0 / 0 | 0 / 0 | 0 / 0 | 2/2 |
| E1+E2+E3 | 2/2 (с 6-го хода) | 0 / 0 | 0 / 0 | 0 / 0 | 1/2 (во 2-м прогоне не извлеклась доля дня, P = 0.45 у порога) |

E3 отдельно, без LLM (слоты 5-го хода ручного прогона, цель не пересмотрена, отказа ещё нет): было солнце 0.45 — лидер, стало 0.36 — лидера нет; после «показания вручную» учёт 0.33 против солнца 0.30.

Регресс `eval.dialog` (9 персон, 8 ходов; добавлена `bakery_no_solar`): база — полнота 34/37, ошибочных полей 0, верный лидер 9/9, заявок 7/9; E1+E2+E3 — 35/37, 0, 9/9, 5/9 (у `grid_losses` и `bakery_no_solar` READY на 8-м ходу вместо 7-го, до заявки не хватило хода; клиент играется LLM, разброс между прогонами такого порядка). Персона `bakery_no_solar` проходит и на базе: LLM-клиент сразу прямо называет цель, поэтому основной инструмент для таких случаев — повтор с заданными репликами.

Батч платформы: все посылки серии собраны в `BATCH_PIPELINE=naive` (в `solution.py` ZIP нет `BATCH_PIPELINE=full`), а в `naive` извлекатель и правила не вызываются — изменения на ответы не влияют. В `full` (40 вопросов `lab/data`, судья v2, 18 с эталонами): `full` базы против A 0.464, `full` E1–E3 против A 0.500, E1–E3 против `full` базы 0.485 — всё в пределах разрешения стенда (±0.03). Ложных отказов в 40 ячейках нет. Для платформы выигрыша не видно: в одиночных вопросах и коротких диалогах отказов почти нет, а польза изменений — в многоходовом чате.

Замечено попутно, не исправлялось: на «а ещё никаких данных не надо?» бот иногда отвечает только вопросом анкеты (вопрос клиента не распознан как вопрос); «490 кВт потребляю» извлекается в мощность, и вопрос про потребление звучит дважды.
