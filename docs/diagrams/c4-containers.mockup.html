Бэкенд ассистента-квалификатора

Один ход диалога проходит фиксированный конвейер. Модель вызывается максимум дважды: извлечь факты и написать ответ. Всё остальное делает код: что спросить, когда идти в базу, какой продукт ведёт и когда пора в заявку.

Компоненты бэкенда

Компонент, код Компонент с вызовом LLM Хранилище Внешнее ①–⑦ порядок шагов одного хода

Пунктир от Contract Registry к Dialogue Policy: политика берёт из реестра веса и шаблоны вопросов. Для этапа 1 solution.py вызывает тот же контроллер, только состояние каждый раз собирается из истории в ячейке, а Session Store и Brief Renderer не участвуют.

Один ход по шагам

ШагКомпонентВход → выходLLM

②State Reducerотбрасывает слот, если quote не найдена в тексте клиента (rapidfuzz ≥ 85). Нормализует единицы. Новое значение заменяет старое, история правок хранитсянет

Данные: откуда, как режем, как достаём

Нужен ли векторный поиск, если есть фильтр по метаданным?Фильтр отвечает на вопрос «в каком продукте искать». Он не отвечает, «какой раздел из 30 в файле ОРЭМ отвечает на этот вопрос». Внутри одного продукта нужен ранжир. Но это не векторная БД: после фильтра остаётся 40–80 чанков, косинус по ним считается numpy за миллисекунды, вектора лежат в памяти. bge-m3 нужен ради перефразов вроде «соседи воруют свет» или «счётчик крутит», где BM25 промахивается.

Чанкинг: автоматически плюс ручная карта

  • Резать руками не нужно: база размечена заголовками. 235 разделов уровня ## и ###, один раздел = один чанк, к тексту приклеен путь файл › раздел › подраздел.
  • Руками делаем карту тегов: файл → продукт и переопределения на уровне раздела. Около часа работы. Это словарь в .py, так что в ZIP этапа 1 он проходит как код, а не как данные.
  • Тег kind по заголовку: faq, fits, not_fits, allowed_facts, forbidden, what_we_do, numbers, other. Правила по тексту заголовка, без LLM.
  • Файлы 10-energy общие, но разделы привязываются: 12-power-thresholds › Пороги оптового рынка → ОРЭМ, 15-microgeneration → СЭС, 13-metering → платформа.

Запрос к базе

cands  = [p for p, prob in scores.items() if prob ≥ 0.25][:2] or ALL_PRODUCTS
pool   = [c for c in KB if c.product in cands + ["general", "energy"]]      # «SQL WHERE»
ranked = rrf(bm25(pool, q), cosine(pool, embed(q)))[:20]
top    = rerank(q, ranked)[:4]
pinned = [c for c in KB if c.product == leader and c.kind in ("forbidden", "not_fits")]
safety = rerank(q, rrf(bm25(KB, q), cosine(KB, embed(q)))[:10])[:2]        # на случай ошибки роутинга
context = dedupe(top + safety + pinned)        # ~1.5–2.5k токенов

Если лучший скор реранкера ниже порога τ (подбираем на eval), политика не отвечает, а уточняет или предлагает специалиста. Это прямо требуется кейсом.

Скоринг продуктов: детерминированно и с объяснением

Фишка: каждое изменение приоритета — сработавшее правило со ссылкой на раздел базы. Менеджер в брифе и жюри в режиме отладки видят, почему бот повёл в эту сторону.

score[p] = prior[p | сегмент]                                  # из 20-portfolio «Навигация по типу компании»
         + Σ  rule.w   для правил, сработавших на ТЕКУЩИХ слотах  # пересчёт с нуля каждый ход
         + Σ  λ^(T−t) · soft[p, t]                               # упоминания, прямые вопросы, масса реранка; λ = 0.7
excluded[p] = любое правило «не подходит»                        # балл не нужен, причина идёт в бриф
P = softmax(score / T) по неисключённым,  T = 2

Жёсткие факты пересчитываются из слотов с нуля, поэтому правка клиента («не 1,1 МВт, а 600 кВт») сразу и корректно меняет картину. Затухают только мягкие сигналы: если клиент спросил про солнце и ушёл в другую тему, интерес гаснет за пару ходов.

Петля диалога и порог заявки

OPEN→DISCOVERY→QUALIFY→READY→CONTACT→SUBMITTED ·NO_CONTACT→ «что подготовить»
Как бот «возвращается» к анкете после ответа?Отдельной ветки возврата нет. Каждый ответ собирается из двух частей: [ответ на вопрос клиента, если он был] + [один вопрос по next_slot, если состояние DISCOVERY или QUALIFY]. Клиент спросил про солнце: бот отвечает по базе и в той же реплике задаёт следующий вопрос анкеты. Автомат при этом остаётся в QUALIFY. Такой формат совпадает со стилем эталонов: в 2/3 из них в конце стоит уточняющий вопрос.
ПереходУсловие (проверяет код)
DISCOVERY → QUALIFYесть лидер: P ≥ 0.45 и отрыв от второго ≥ 0.15, либо два кандидата по P ≥ 0.25. До этого спрашиваем различающие слоты: сегмент, цель («платёж / учёт / потери / надёжность»).
QUALIFY → READYу каждого кандидата заполнены «пропускные» слоты (ОРЭМ — мощность, СЭС — кровля или площадка, платформа — число приборов, потери — тип организации) и ≥ 75% обязательных слотов, где отказ «не знаю» считается закрытым.
любое → CONTACTwants_contact; вопрос вне базы (реранк < τ) или по 02 › Когда требуется специалист; 8 ходов в QUALIFY без прогресса.
READY → CONTACTбот один раз предлагает заявку и показывает, что уже собрано. Отказ ведёт в NO_CONTACT.
NO_CONTACTотвечаем дальше. Повторный призыв не раньше чем через 3 хода. Отдаём список документов из 03-calculation и опросного листа (п. 4, 8, 10, 11, 13, 14).
CONTACT → SUBMITTEDесть ФИО, телефон (валидатор формата), компания и согласие на ПДн → ⑦ бриф.

Как выбирается next_slot

value(slot) = Σ_p∈кандидаты P(p) · weight(slot, p)      # вес из Contract Registry
            + 1.0  если slot — «пропускной» для кандидата
            + 0.5  если slot различает двух лидеров            # мощность различает ОРЭМ и СЭС
            − ∞    если уже спрошен дважды или клиент отказался
next_slot = argmax(value)  →  шаблон вопроса из реестра (LLM только переформулирует под контекст)

Когда ассистент идёт в базу

Решает политика, а не модель. Модели не дают инструментов, поэтому «полез в базу, когда взбрело» невозможно. На ход максимум один поиск плюс выборки по id.

Событие ходаПоискЧто берём
Клиент задал вопрос (intent=question или смешанный)дафильтр по кандидатам + top-2 без фильтра + закреплённые
Клиент только ответил на вопрос анкетынетподтверждение строится из трассы правила («1,1 МВт — выше порога 750 кВт»), чанк-источник берём по id
Сменился лидернеткарточка продукта по id: «Не подходит, если», «Чего утверждать нельзя». Кэшируется в сессии
Переход в READY / NO_CONTACTнетраздел 03-calculation › Для <продукта> по id
Вне темы или нужен специалистнет02 › Когда требуется специалист по id
Этап 1, одиночный вопросдакак первый случай, состояние собирается из истории
